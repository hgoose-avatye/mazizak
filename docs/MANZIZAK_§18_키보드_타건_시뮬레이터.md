## 18.0 결론 요약

1. **방향은 채택한다** [추천]: 키보드를 "버튼형 ASMR"에서 "스위치를 바꾸면 움직임과 소리가 함께 달라지는 타건 장난감"으로 넓힌다. 다만 **'재현'이 아니라 '표현'**이다. 휴대폰 유리면은 압력, 걸림, 클릭의 촉감을 전달할 수 없다.
2. **분류 축을 다시 잡는다** [추천]: 다섯 메커니즘은 같은 층위가 아니다.
   - **느낌**: 리니어 / 택타일 / 클릭
   - **저소음**: 앞의 느낌에 붙는 수식어
   - **감지 방식**: 접점 / 자석(HE) / 광학
   - **사운드 스타일**: 위 축들과는 별도 속성이다(조약돌·까랑까랑·보글보글·서각서각).
3. **차이를 전달하는 주 채널은 소리다** [추정, 근거 18.2]: 실물 타건은 수십 ms 안에 끝나서 60fps 화면에서는 1~2프레임이다. 그래서 택타일 걸림은 눈으로 구별되지 않는다. 화면에서 기대할 수 있는 차이는 *올라오는 움직임*과 *바닥 안착 방식(저소음)* 정도다.
4. **콘텐츠 범위** [결정됨: 2026-11-09 사용자]
   - 현재 조약돌·까랑까랑 2종을 유지한다.
   - 초기 확장 목표는 **타건음 4종 이상**, 최종 목표는 **약 25종 스위치**다.
   - 2종은 상한이 아니라 현재 상태일 뿐이다.
   - 5분류(리니어·택타일·클릭·저소음·자석)를 유지하고, 메커니즘과 사운드 스타일은 분리 관리한다.
5. **두 등급을 구분한다** [결정됨 + 18.6 세부]
   - **"검증된 스위치 녹음"**: 같은 보드에서 실제 해당 스위치를 녹음한 세트. 메커니즘 라벨을 붙일 수 있다.
   - **"ASMR 스타일 프리셋"**: CC0 등 출처가 서로 다른 소리 결. 소리 결 이름만 쓴다.
   - 지금 있는 2종은 서로 다른 보드·방·마이크에서 녹음돼 스타일 프리셋 등급이다.
6. **우선순위** [결정됨]: 키보드 스위치·일반 말랑이·음식형 스퀴시·슬랑이·왁뿌볼·크런치 말랑이는 **모두 핵심 카테고리**다. 출시 순서는 기술 위험 순으로 웨이브를 나누되(18.8, §19), 말랑이 완료나 특정 녹음 장비 확보를 키보드 콘텐츠 추가의 선행 조건으로 두지 않는다.

## 18.1 스위치 유형별 비교표

### 18.1.1 분류 재정의 [추천]

| 축 | 값 | 사용자가 체감하는 것 | 시뮬레이터에서 표현 가능한가 |
|---|---|---|---|
| 느낌(family) | linear / tactile / clicky(click-jacket, click-bar) | 걸림의 유무, 클릭 | **소리로 가능.** 화면 표현은 제한적 |
| 저소음(silent) | on / off | 바닥·복귀 충격이 작고 둔탁함 | 소리로 가능. 화면에서는 "얕고 부드러운 안착" 정도 |
| 감지(sensing) | contact / magnetic(HE) / optical | 작동점 조절, Rapid Trigger(펌웨어 기능) | **탭 입력으로는 불가.** 깊이 정보가 없다 |
| 사운드 스타일 | 조약돌 / 까랑까랑 / 보글보글 / 서각서각 | 소리의 결(키캡·보강판·케이스·흡음·윤활) | 녹음 세트로 가능 |

- HE는 **자석 위치를 감지하는 방식**이다. 자기 부상이나 마찰 없는 행정이 아니다. 기계적 느낌은 대부분 리니어다 [확인: wooting.io, Gateron].
- Razer 아날로그 스위치는 HE가 아니라 **광학(Analog Optical Gen-2)**이다. 작동점은 0.1–4.0 mm다 [확인: Razer 뉴스룸].
- Silent Lime(Outemu Silent Lime V3)은 **저소음 택타일**이다 [확인: 판매처 다수]. 원래 후보 목록에서 택타일과 저소음 양쪽에 들어 있던 이유가 이것이다.

## 18.2 키 입력 상태 및 애니메이션 설계

### 18.2.1 상태 머신 (키별)

```
IDLE ─pointerdown/keydown(holders 0→1)─► PRESSING ─► [BUMP] ─► ★click ─► ★bottom ─► HOLD
  ▲                                                                                   │
  │                                            pointerup/cancel/keyup(holders→0)      ▼
  └──────── SETTLING ◄── ★topout ◄── (클릭바: ★upClick) ◄──────────────────── RELEASING
            RELEASING/SETTLING 중 재입력 → PRESSING (현재 위치에서 이어서)
```

- 한 키를 여러 입력(포인터 id, 물리 키)이 동시에 붙잡을 수 있다(holders 집합, 현행 유지). 키는 holders가 하나라도 남아 있으면 눌린 상태다 [확인: model.ts].
- 현재 위치에서 다시 누르는 동작은 현행 구조에서 이미 성립한다 [확인: model.ts]. 바꿔야 하는 것은 복귀 곡선과 이벤트 정의다.
- 물리 키보드 입력도 같은 상태 머신을 쓰고, `ev.repeat`는 무시한다(현행).

### 18.2.2 터치에서 알 수 있는 것과 없는 것 [확인: 하드웨어 사실]

- `pointerdown`은 "손가락이 닿았다"는 신호일 뿐이다. 힘·속도·깊이는 알 수 없다(압력 미사용 [결정됨] §6.3). 그래서 **행정은 손가락이 미는 것이 아니라 재생되는 애니메이션이다.**
- 세기는 §6.3 모델(연타 간격, 누른 시간)로 추정한 스칼라 하나만 쓰고, 바닥음 게인과 복귀 세기에만 반영한다 [가설].
- 휴대폰은 압력, 범프의 저항, 클릭의 촉감을 **재현할 수 없다.** iOS 웹에는 진동 API가 없고, Android `vibrate`는 세기를 조절할 수 없다 [확인: MDN]. **이 한계는 사용자 문구에도 밝힌다** [추천]. 예: "실제 스위치의 압력과 걸림은 화면에서 느낄 수 없어요. 소리와 움직임으로 차이를 표현했어요."

### 18.2.3 지각 가능한 차이 [추정]

오프라인 1D 힘곡선 시뮬레이션(질량·손가락 힘은 가정값)으로 계산하면 모든 아키타입이 약 25 ms 안에 바닥에 닿는다. 60fps에서 1~2프레임이고, 탭 순간이 프레임 중간 어디에 떨어지는지도 무작위다. **이것은 측정값이 아니라 모델 추정이다.**

| 표현 요소 | 지각 가능성 | 채택 |
|---|---|---|
| 소리(바닥음 결, 클릭, 복귀음) | 높음 | **주 채널** |
| 올라오는 속도·모양 | 중간 | 채택 |
| 저소음의 얕고 부드러운 안착(반동 없음) | 낮음~중간 | 채택 |
| 택타일·클릭 1프레임 걸림 | 낮음, 일관되지 않음 | 넣되 **판정 기준으로 쓰지 않음** |
| 상단 반동(0.1 mm 미만), 범프 위치 차이 | 없음 | 넣지 않음 |
| 카메라 흔들림, 찌그러짐, 파티클 | — | **과장이므로 금지** |
| 메커니즘별 총행정 차이(3.3 vs 4.0 mm) | 화면상 1~2 px | 넣지 않음 |

### 18.2.4 애니메이션 파라미터 [가설: 실기기·청취 후 조정]

- **누름**: 현행 `down {freq 38, ζ 1.0}`을 유지한다. 바닥 도달이 약 16 ms(1프레임)라서 이미 충분히 빠르다 [확인: 해석해].
- **복귀 — 결함 수정 필요** [확인: model.ts:21]: 현행 `up {freq 17, ζ 0.5}`는 키를 **휴지 위치보다 행정의 약 16% 위로** 튀어 오르게 한다(화면상 1~2 px). 실물 스템은 상단 하우징에 막혀 멈춘다. → **상단 하드 스톱(클램프 + 작은 반발계수)**으로 바꿔서, 튕김이 생기더라도 행정 안쪽(아래)으로만 생기게 한다.
- **프리셋별 차이**(2프리셋 단계부터 적용 가능):

| 성격 | 복귀 | 바닥 | 키 흔들림(누른 위치 기울기) |
|---|---|---|---|
| 묵직(조약돌·리니어) | 약간 느리게, 하드 스톱 반발 0.1 | 단단함 | 중간 |
| 경쾌(까랑까랑·클릭) | 빠르게, 반발 0.15 | 단단함 | 작음 |
| 저소음(향후) | 부드럽게 감속 안착, 반발 0 | 0.9~0.94 지점에서 멈춤(댐퍼) | 감쇠 강화 |

- **시각 행정**: 현행 `vis.travel 0.13`(약 2.5 mm 상당)을 유지한다. 실제 비율 0.21로 올렸을 때 지각상 이득이 있다는 근거가 없다.
- **스페이스바**: 스테빌라이저가 양끝을 묶으므로 좌우 기울기는 일반 키의 절반 이하로 한다. 시각적 덜컹임은 넣지 않는다.
- **동시 입력·연타**: 키별 상태는 독립이다. 다른 키끼리 시각적으로 엮지 않는다(케이스 흔들림 없음).
- 정밀 힘곡선 LUT·역탐색·서브스텝은 **보류**한다. 위 표의 결론과 맞지 않는 과잉 설계다.

## 18.3 타건음 재생 아키텍처

### 18.3.1 타건음의 레이어 구조 (설계 근거)

| 레이어 | 원인 | 소유 |
|---|---|---|
| 마찰 | 스템·스프링 긁힘 | 메커니즘(윤활 영향 큼) |
| 범프 | 택타일 리프 통과 | 메커니즘 |
| 클릭 | 재킷/바 | 메커니즘. 바닥보다 먼저 난다 |
| 바닥 충격 | 스템·키캡 → 보강판·케이스·흡음 | **스타일**(소리 결의 대부분) × 저소음 감쇠 |
| 복귀 충격 | 스템 → 상부 하우징 | 스타일 × 저소음 감쇠 |
| 스프링 핑 | 스프링 공진 | 스타일. 결함음으로 보고 기본 OFF |
| 스테빌 덜컹 | 스페이스 와이어 | 스타일 + 키 그룹 |

### 18.3.2 방식 결정 [추천]

| 방식 | 사실감 | 비용 | 판단 |
|---|---|---|---|
| **프리믹스**: 녹음 세트 1개 = 프리셋 1개 | 높음(클릭과 바닥이 같은 보드에서 울림) | 프리셋 수에 비례 | **MVP와 4종 단계에서 채택** |
| 레이어 런타임 합성: 메커니즘 ⊕ 스타일 | 중간(공간감 불일치 위험) | 보이스 2~3배 | 보류 |
| 레이어 다운로드 + 선택 시 베이크 | 중간 | 다운로드·메모리 유리 | 프리셋이 6종을 넘거나, 블라인드 테스트(T1)에서 오버레이가 구별되지 않을 때만 검토 |

- 녹음 세션에서 레이어 재료(클릭 단독, 스테빌 단독, 리니어 바디)를 **함께 모아만 둔다**(세션당 30~60분 추가로 추정).

### 18.3.3 재생 규칙

- **키다운 소리는 `pointerdown` 핸들러 안에서 즉시 `start(0)`**한다(현행). rAF를 거치면 0~16.7 ms가 늘어난다 [확인: bench-1x.json handlerToFrame p50 15.4 ms]. 키업은 `pointerup`에서 재생한다.
- 클릭 → 바닥 간격은 **프리믹스 녹음에 자연스럽게 들어 있으므로 런타임 오프셋은 두지 않는다.** 화면이 소리보다 약 1프레임 늦는 것은 허용한다(소리가 먼저 오는 쪽이 덜 거슬린다 [추정]).
- **반복감 방지**:
  - 라운드로빈(직전 1~2개 제외)과 피치 ±20~30 cent, 게인 ±1~1.5 dB 변주(현행).
  - **재생 중인 같은 버퍼는 다시 고르지 않는다.** 같은 샘플이 수 ms 차이로 겹치면 콤 필터가 생긴다.
  - 연타 덕킹은 계단식이 아니라 연속값으로 한다.
- **동시 입력**:
  - 보이스 풀은 24(현행)로 유지한다.
  - **키당 최대 2보이스 상한을 추가한다**(현재 없음 [확인: audio.ts]).
  - 보이스를 빼앗는 순서는 ① 같은 키의 초과분 → ② 꼬리 → ③ 가장 오래된 것이다. 시작한 지 30 ms 미만인 트랜지언트는 보호한다.
  - 화음 감쇠(약 1/√N)를 유지하되, 연타 감쇠와 이중으로 적용되지 않게 한다(현재 이중 적용 [확인: toy.ts:117-121]).
- **지연 목표** [가설]: 스피커 기준 터치→소리 p50 ≤ 50 ms, p95 ≤ 70~80 ms. 블루투스는 목표에서 빼고 안내만 한다.
  - 모바일 수치는 전부 [추정]이며 240fps 촬영으로 실측한다(§13 A3).
  - **§15 킬 기준 3(스피커 지연)을 먼저 확인하는 것이 시뮬레이터 작업의 전제다.**
- **메모리·로딩** [계산]:
  - 프리셋 1종(54샘플, 약 7.7 s, 모노 f32 48 kHz)은 약 1.5~1.9 MB, 4종이면 약 6~8 MB다.
  - 진입할 때는 활성 프리셋만 로드한다.
  - 이웃 프리셋은 idle 시간에 미리 받는다.
  - 장난감을 나가면 해제한다(현재 해제하지 않음 [확인]).
  - 전환 직후 아직 로드되지 않은 프리셋은 **무음이 되지 않도록** 이전 프리셋이나 합성음으로 대체한다(현재 무음 [확인: toy.ts:94-114]).
- 포맷(FLAC/AAC 스프라이트)은 녹음을 확보한 뒤 블라인드 A/B로 결정한다. AAC는 앞부분 priming 무음 때문에 스프라이트 오프셋 보정이 필요하다 [확인: 일반 사실].

## 18.4 스위치·사운드 프리셋 데이터 모델 [추천: MVP에 필요한 최소형]

```ts
type Feel = 'linear' | 'tactile' | 'clicky-jacket' | 'clicky-bar';
type Sensing = 'contact' | 'magnetic' | 'optical';           // UI 노출 안 함(MVP)
type SoundStyle = 'pebble' | 'clack' | 'creamy' | 'soft';    // 조약돌/까랑까랑/보글보글/서각서각

interface SwitchProfile {           // 움직임(18.2)
  feel: Feel;
  silent: boolean;
  sensing: Sensing;
  motion: { upFreq: number; upDamping: number; topRestitution: number; bottomStop: number; tiltDamping: number };
}

interface SampleSet {               // 녹음 1세트 = 프리믹스(18.3)
  sprite: string;                   // 스프라이트 파일
  roles: Record<'down' | 'up' | 'spaceDown' | 'spaceUp', string[]>;  // 슬라이스 id
  provenance: 'self-recorded' | 'cc0' | 'proxy' | 'synth';          // proxy = 대체 샘플(예: 스페이스바 없음)
  recordedOn: { board: string; switchModel?: string };              // 내부 기록 전용, UI 비노출
}

interface KeyboardPreset {
  id: string;
  label: string;                    // 의성어 이름만(§8.2 상표 정책)
  subLabel?: string;                // 예: "리니어 · 묵직" — 같은 보드에서 스위치만 바꿔 녹음한 세트일 때만
  style: SoundStyle;
  switch: SwitchProfile;
  samples: SampleSet;
  visualStyle: string;              // 키캡·케이스 외형 = 녹음한 보드의 결에 묶는다
}
```

- **라벨 규칙**: `subLabel`(메커니즘명)은 `samples.provenance === 'self-recorded'`이고, 비교 대상 프리셋과 `recordedOn.board`가 같을 때만 노출한다. 서로 다른 보드에서 녹음한 CC0 세트에는 소리 결 이름만 쓴다.
- **폴백**: 스페이스바 누락 → 일반 키 rate 0.85~0.9 (`proxy`), 키업 누락 → 다운의 약한 테이크 −8 dB (`proxy`), 로드 실패 → 절차적 합성(현행).
- 레이어 합성용 타입(`MechanismProfile.layers`, `bodyMod` 등)은 레이어 방식을 채택할 때 추가한다(`research/keyboard-sim/audio.md` §5에 스케치가 있다).

## 18.5 실사형 키보드 UI 구성안

```
┌────────────────────────────────┐ 390×844 (세로)
│ ‹  키보드               🔊  ⋯  │
│    ┌──────────────────────┐    │
│    │  [만] [지] [작]      │    │  1u ≈ 80pt (현행 유지)
│    │  [◇ ] [♪ ] [★ ]      │    │  ↺ 레전드 → 다른 기호(초기화 버튼과 혼동 방지)
│    │  [1 ] [2 ] [3 ]      │    │
│    │  [   스페이스    ]   │    │
│    └──────────────────────┘    │
│          묵직 · 둥근 소리       │ ← 보조 라벨 1줄(전환 직후 1.5초 진하게)
│     ┌────────┬────────┐        │
│     │ 조약돌 │까랑까랑│        │ ← MVP: 칩 2개 / 게이트 통과 후 4개
│     └────────┴────────┘        │
└────────────────────────────────┘
```

| 항목 | 결정 |
|---|---|
| 스위치 선택 | **하단 칩**. 칩을 탭하면 가운데 키(♪)가 스스로 한 번 타건한다(**시연 1타**). 칩만 연달아 눌러도 비교가 끝난다 [추천]. 움직임 줄이기가 켜져 있으면 소리만 낸다 |
| 초기화 버튼 | 키보드 화면에서는 제거한다(키는 항상 원위치로 돌아온다). 남는 자리를 칩에 준다 |
| 외형 | 키캡·케이스는 **녹음한 보드의 결**에 묶는다(현행 `setStyle` 유지). 같은 보드에서 스위치만 바꾼 세트끼리는 외형을 같게 두고, 스템 색 같은 작은 단서만 바꾼다 |
| 이름 | 의성어가 주인공이다. "재현", "똑같은", 제품명, 상표성 색 호칭(적축·갈축·청축)은 금지한다. 4번째 프리셋 이름(서각 vs 툭툭)은 **녹음을 들어본 뒤 5초 인지 테스트로 정한다** |
| 문구 | 설정 하단: "스위치 소리는 직접 녹음했으며 특정 제품의 소리를 재현하지 않습니다." + 18.2.2의 한계 문구 |
| 카메라 | 현행 유지. 키 옆면을 더 보이게 낮추는 안은 히트 영역 실측 뒤 [가설] |
| 첫 10초 | 진입 → 유휴 시연(키 3개가 또르륵) → 손가락 고스트 1회 → 2~3타 뒤 "스위치를 바꿔보세요" 힌트 1회 |
| 입력 | 터치·마우스·물리 키보드(QWE/ASD/ZXC + 넘패드 789/456/123). 손가락이 미끄러져도 누른 키를 뗄 때까지 유지하고, 쓸어치기는 v1.1이다. 동시 입력은 최대 5키 |
| 진동 | [결정됨 v0.2] **기본 OFF, 사용자가 켤 때만 ON.** 기능 감지(`navigator.vibrate` 유무)로 지원하지 않는 환경(iOS 웹 등)에서는 항목을 숨기거나 비활성으로 두고, 나머지 기능은 정상 동작한다. 진동으로 스위치별 실제 압력이나 걸림을 재현한다고 주장하지 않는다. 문구는 "가벼운 진동 피드백" 정도로 쓴다. 현 코드는 `settings.ts` 기본값이 ON이라 **기본값 변경이 필요하지만, 이번 승인 범위(C1~C3) 밖이라 아직 반영하지 않았다** |
| v1.1 이후 | 스위치 엿보기(키캡이 들리며 스위치가 보이는 연출), 2×2 비교 판(스위치 테스터), 직접 조합 시트(성립하는 조합만), 스위치 실험실(HE 작동점·Rapid Trigger를 드래그로 시연) |

### 18.6.3 게이트 통과 후 목표 구성

| 프리셋 | 느낌 | 저소음 | 소리 결 | 키다운:키업(§8.2) |
|---|---|---|---|---|
| 묵직한 리니어 (도각·조약돌) | linear | off | 조약돌 | 1 : 0.5~0.6 |
| 경쾌한 택타일 (또각·타각) — *G4 통과 시* | tactile | off | 까랑까랑 쪽 | 1 : 0.8~1.0 |
| 클릭형 (찰칵·딸깍) | clicky-bar | off | 중립~밝음 | 클릭바라 키업에도 클릭 |
| 저소음 리니어 (서각 또는 툭툭) | linear | on | 서각서각 | 1 : 0.2~0.3 |

- **HE는 프리셋으로 만들지 않는다.** 탭으로는 장점을 보여줄 수 없다.
- **보글보글**은 4번째 자리를 다툰 후보지만, 리니어+조약돌과 귀로 구분되는지(T3) 확인될 때까지 보류한다.

## 18.8 다른 장난감과의 우선순위 — v0.2

[결정됨] 6개 카테고리(기계식 키보드 스위치, 일반 말랑이, 음식형 스퀴시, 슬랑이, 왁뿌볼, 크런치 말랑이)는 **모두 핵심 콘텐츠**다. 각 카테고리는 외형이 아니라 물성, 조작 반응, 사운드가 달라야 한다. 아래는 "제외"가 아니라 **기술 위험·재사용 순서에 따른 출시 웨이브 제안**이다 [추천, 세부는 §19.2].

| 웨이브 | 내용 | 근거 |
|---|---|---|
| W1 | 키보드 결함 수정(완료, 18.9) → 키보드 4소리 이상 / 말랑이 TPR 재질 추가(폼 유지) | 기존 코어를 재사용하고 데이터만 추가한다. 위험이 낮다 |
| W2 | 음식형 스퀴시, 크런치 말랑이 | SquishyCore 재사용 + 형태·스킨·그레인 모디파이어 |
| W3 | 왁뿌볼 | 상태 머신 + 사전 프랙처 에셋이 필요하다. 아트 비용이 가장 크다 |
| W4 | 슬랑이 | 소성(형상이 남음)은 하이트필드라는 새 코어가 필요하다 |

- 웨이브는 병렬로 진행할 수 있다. 키보드 콘텐츠 추가는 말랑이 진행 상황이나 녹음 장비 확보를 기다리지 않는다 [결정됨].
