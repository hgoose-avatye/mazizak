## 0. 한 줄 결론

**"같은 키보드, 다른 속"**: 판(키캡·케이스)은 그대로 두고 **스위치만 바꾼다**. 하단 칩 4개로 고르고, **칩을 누르는 순간 가운데 키가 한 번 스스로 타건(시연 1타)** 해서 차이를 귀와 눈으로 바로 비교하게 한다. 스위치 테스터 배치와 메커니즘×소리 2축 피커는 v1.1 이후 "더 깊이" 경로로 미룬다. [추천]

## 1. 현재 상태 진단 (코드·스크린샷 기준)

| 항목 | 현재 | 시뮬레이터 관점의 문제 |
|---|---|---|
| 프리셋 | 조약돌 / 까랑까랑 2종, `KEY_PRESET_INFO`에 label+desc | **소리 스타일 이름**이라서 "스위치가 바뀐다"는 프레이밍이 없음 |
| 전환 시 외형 | `vis.setStyle(p)` → 키캡·케이스 외형도 함께 바뀜 | "같은 키보드인데 스위치만 달라진다"는 목표와 정반대. 차이가 외형 때문인지 스위치 때문인지 구분 불가 |
| 전환 피드백 | 칩 선택만 바뀜, 소리 없음 | 비교하려면 칩 → 키로 손을 옮겨 다시 쳐야 함(A/B 속도 저하) |
| 키 움직임 | 모든 프리셋이 같은 스프링(`DEFAULT_KB_PARAMS`) | 움직임으로는 차이가 0 |
| 하단 바 | 좌: 칩 2개, 우: 초기화 | 키보드에서 초기화는 의미가 거의 없음(키는 늘 원위치). 칩 4개가 들어갈 자리를 차지 |
| 레전드 | 만/지/작/↺/♪/★/1/2/3 | `↺` 레전드 키가 초기화 버튼과 같은 기호 → 혼동 가능 [검증필요] |
| 개발 라벨 | "SFX B 녹음" 배지 | 출시 화면에서는 숨김 필요 |

## 2. 스위치 선택 UX — 4안 비교

### 2.1 후보

**A. 세그먼트 칩 4개 (현행 확장)**
```
┌──────────────────────────────┐
│        (키보드 3D)            │
│                              │
│ [도각][또각][찰칵][서각]       │  ← 한 번에 1개, 판 전체가 그 스위치
└──────────────────────────────┘
```

**B. 스와이프 스위치 트레이 (3D 스위치 실물 카드)**
```
┌──────────────────────────────┐
│        (키보드 3D)            │
│  ‹  ┌────┐ ┌────┐ ┌────┐  ›  │
│     │ ▣  │ │ ▣  │ │ ▣  │     │  ← 투명 하우징 스위치 3D 썸네일
│     │도각│ │또각│ │찰칵│      │
│     └────┘ └────┘ └────┘     │
└──────────────────────────────┘
```

**C. 스위치 테스터 배치 (9키에 서로 다른 스위치)**
```
┌──────────────────────────────┐
│   ┌──┐ ┌──┐ ┌──┐             │
│   │도│ │도│ │도│  ← 1열: 도각 │
│   ├──┤ ├──┤ ├──┤             │
│   │또│ │찰│ │서│  ← 혼합      │
│   ...                        │
└──────────────────────────────┘
```

**D. 2축 피커 (메커니즘 × 소리 스타일)**
```
┌ 스위치 ───────────────────────┐
│ (리니어)(택타일)(클릭)(저소음)(자석)│
│ 소리                          │
│ (조약돌)(까랑까랑)(보글보글)(서각서각)│
└──────────────────────────────┘
```

### 2.2 평가 (1~5, 5가 좋음) [가설: 사용성 테스트로 확인]

| 기준 | A 칩 4개 | B 트레이 | C 테스터 | D 2축 |
|---|---|---|---|---|
| 발견성(뭘 바꿀 수 있는지) | 4 | 5 | 2 (설명 없으면 "버그?") | 3 |
| 비교 속도(A/B) | 3 → **시연 1타 추가 시 4** | 3 | **5** (옆 키 탭 = 즉시 비교) | 2 |
| 화면 혼잡 | 5 | 2 (세로 120pt+ 점유) | 4 | 1 |
| 엄지 도달 | 5 (하단 한 줄) | 4 (가로 스와이프 충돌 위험) | 5 | 2 (2줄·시트) |
| "같은 키보드, 다른 스위치" 목표 | **5** (판 전체가 한 스위치) | 5 | 3 (한 판이 뒤섞여 '내 키보드' 느낌 약함) | 4 |
| 첫 타건까지 지연 | 0 (기본값 바로 타건) | 0 | 0 | 0, 단 선택 피로 큼 |
| 구현·에셋 비용 | 낮음 | **높음**(3D 스위치 모델 4종, 추가 드로우콜, 썸네일) | 낮음~중(키별 프리셋, 보이스 관리) | 중(조합 20개 사운드 = 녹음 폭증) |
| 경쟁작(20종 스위치)과의 차별 | 중 | 낮음(목록 UI는 앱과 같은 축) | **중상**(실물 테스터 은유, 웹 즉시) | 낮음(조합 수 경쟁) |

### 2.3 판단

- **MVP = A안 + "칩 탭 시 시연 1타"** [추천]
  - 칩을 누르면 판 전체 스위치가 바뀌고, 0.15초 뒤 **가운데 키(♪)가 스스로 한 번 눌렸다 올라오며** 그 스위치의 키다운/키업 소리를 낸다.
  - 결과적으로 **칩 4개를 연달아 톡톡 누르는 것만으로 4종 비교가 끝난다**. C안의 비교 속도 장점을 A안 안에 가져온다.
  - 사용자가 키를 누르고 있는 중(held > 0)이면 시연 생략. 같은 칩 재탭 시에도 시연(“다시 들어보기”).
- **C안(테스터)은 v1.1 "비교 모드"로** [추천]: 9키 판을 섞는 대신, **별도 레이아웃(2×2 테스터 판, 투명 키캡)** 으로 분리. 메인 키보드의 일관성을 해치지 않는다. 경쟁작 대비 "실물 스위치 테스터를 손끝으로" 라는 차별 은유가 있어 보류 가치 큼. [가설]
- **D안 2축은 MVP 제외** [추천]
  - 축이 독립적이지 않다: 보글보글(돔+스프링 계열)은 메커니즘이 다르고, 클릭+서각서각 같은 조합은 실물에서 성립하기 어렵다. 20칸 중 상당수가 "가짜 조합".
  - 조합마다 녹음/합성 필요 → §8.2 프리셋당 55~70샘플 × 조합 수.
  - 내부 데이터 모델은 2축으로 두되(아래 §2.5), UI는 프리셋 단위로 노출.
- **B안 트레이는 비용 대비 효과 낮음**: 화면 세로를 크게 먹고 키보드를 작게 만든다. 3D 스위치 모델은 §3.3 "스위치 엿보기"에서 한 번만 쓰고, 트레이는 만들지 않는다.

### 2.4 확장 경로 [추천]

| 단계 | 내용 | 진입 위치 |
|---|---|---|
| MVP(키보드 시뮬 v1) | 프리셋 4칩 + 시연 1타 + 프리셋별 움직임 프로파일 + 스위치 엿보기 | 하단 칩 |
| v1.1 | **비교 모드**(2×2 테스터 판) — 4스위치를 나란히 | 칩 줄 끝 `⇄ 비교` 버튼 또는 칩 길게 누르기 |
| v1.2 | **직접 조합 시트**: 메커니즘 × 소리 스타일, 성립하는 조합만 활성화(불가 조합은 회색 + "실물에서 드문 조합") | ⋯ 메뉴 > "스위치 직접 고르기" |
| v1.3+ | **참고 카드**: 스위치 계열 설명(무게감·구분감·소음), 녹음 환경 메모. 브랜드명 없음(§3.3) | 비교 모드의 각 스위치 길게 누르기 |
| 보류 | 자석식(HE): 터치는 압력이 없어 "작동점 조절/래피드 트리거"의 핵심 가치를 전달 불가. 물리 키보드 입력에서도 의미 없음. 소리만으로는 리니어와 구분 어려움 → **MVP·v1.1 제외** [추천], 넣는다면 "가볍고 매끈한 리니어" 소리 프리셋으로만 [미결정] |

### 2.5 데이터 모델 메모 (UX 관점 요구사항)
- `SwitchPreset = { mechanism, soundStyle, motionProfile, label, onomatopoeia, desc }` 형태로 두 축을 **내부에서는 분리**. 칩 4개는 이 중 큐레이션된 4조합.
- 프리셋 선택은 `settings.keyPreset`처럼 저장(재방문 시 유지). 단 **처음 방문자의 기본값은 1번(도각)** 고정. [추천]
- 키캡/케이스 외형은 프리셋과 분리(향후 스킨 축). 현재 `vis.setStyle(p)` 연동은 끊는 것을 권장. [추천, 단 아래 §6 "최소 변경"에서 순서 조정]

## 3. 이름 · 카피

### 3.1 원칙 [추천]
1. **의성어가 주인공**, 메커니즘 용어(리니어/택타일/클릭)는 작은 보조 텍스트. P1·P2(일반)는 소리로, P3(키보드 관심층)는 용어로 알아본다.
2. 브랜드·제품명·제품 고유 색 호칭 없음(§8.2). "○○축", "○○ 스위치 소리", "××키보드 감성" 금지.
3. "재현", "똑같은", "정품" 같은 단어 금지. 대신 "느낌", "결".
4. 2글자 칩(엄지 탭 영역 확보, 390pt 폭에 4개 + 여백).

### 3.2 프리셋 이름안

| # | 칩(의성어) | 보조 라벨(작게) | 한 줄 설명 | 메커니즘 / 소리 스타일(내부) |
|---|---|---|---|---|
| 1 | **도각** | 리니어 · 묵직 | 걸림 없이 쑥, 바닥에서 둥글게 도각. | Linear / 조약돌 |
| 2 | **또각** | 택타일 · 경쾌 | 중간에 톡 걸리고, 가볍게 또각. | Tactile / 까랑까랑(밝은 쪽) |
| 3 | **찰칵** | 클릭 · 또렷 | 누르는 도중 찰칵, 확실한 손맛. | Clicky / 까랑까랑 |
| 4 | **서각** | 저소음 · 조용 | 바닥이 폭신해서 서각, 툭툭. | Silent linear / 서각서각 |

- 대안 칩: 도각/타각/딸깍/툭툭. "서각"은 일상어가 아니라 낯설 수 있음 [검증필요: 5초 인지 테스트]. 낯설면 **툭툭**으로 교체.
- 보글보글 소리 스타일은 4번 자리를 다투는 후보. "조용함"(P1 회의 대기 시나리오)이 더 쓸모 있다고 보고 서각을 넣음 [가설].
- 화면 제목: "키보드" 유지. 칩 그룹 aria-label: "스위치". (현재 "타건감")

### 3.3 "참고 스위치" 표기 정책 [추천, 법무 확인은 검증필요]

| 층위 | 무엇을 적나 | 예 |
|---|---|---|
| **UI(앱 화면)** | 일반 계열명 + 성질만 | "리니어 계열 · 걸림 없음 · 무게감 있음" |
| **UI 금지** | 제조사·제품명·상표성 색 호칭(적축/갈축/청축 등)·"○○ 느낌" | ✕ "○○ 적축 소리" |
| **출처/크레딧 문서** | 녹음 장비·환경의 일반 서술 | "윤활한 리니어, 두꺼운 PBT 키캡, 폼 보강 케이스에서 직접 녹음" |
| **내부 기록(비공개)** | 실제 사용 부품 모델명 | 녹음 시트 · 스프라이트 메타데이터 주석 |

- 스템 색(축 색) 시각 큐: 업계 관습 색(빨강=리니어, 갈색=택타일, 파랑=클릭)을 그대로 쓰면 특정 제품군을 연상시킨다. **자체 팔레트**(예: 도각=먹색, 또각=호박, 찰칵=청자, 서각=연회색 반투명)를 권장 [미결정: P3가 관습 색을 기대하는지 vs 법무 리스크].
- 카피 예: 설정 시트 하단 "스위치 소리는 자체 녹음한 것으로, 특정 제품의 소리를 재현하지 않습니다." [추천]

## 4. 화면 구성 (세로 우선)

### 4.1 메인 화면 와이어프레임 [추천]

```
┌────────────────────────────────┐ 390×844
│ ‹  키보드               🔊  ⋯  │ 상단바(현행 유지)
│                                │
│                                │
│    ┌──────────────────────┐    │
│    │ ┌────┐┌────┐┌────┐   │    │
│    │ │ 만 ││ 지 ││ 작 │   │    │  1u 키 76~88pt
│    │ └────┘└────┘└────┘   │    │  (현 스크린샷 ≈ 80pt 유지)
│    │ ┌────┐┌────┐┌────┐   │    │
│    │ │ ◇  ││ ♪  ││ ★  │   │    │  ↺ 레전드는 ◇ 등으로 교체 권장
│    │ └────┘└────┘└────┘   │    │  ♪ = 시연 1타가 일어나는 키
│    │ ┌────┐┌────┐┌────┐   │    │
│    │ │ 1  ││ 2  ││ 3  │   │    │
│    │ └────┘└────┘└────┘   │    │
│    │ ┌──────────────────┐ │    │
│    │ │      스페이스      │ │    │
│    │ └──────────────────┘ │    │
│    └──────────────────────┘    │
│                                │
│        리니어 · 묵직            │ ← 보조 라벨 1줄(작고 흐림)
│ ┌──────┬──────┬──────┬──────┐  │
│ │ 도각 │ 또각 │ 찰칵 │ 서각 │  │ ← 칩 4개, 하단 안전영역 위
│ └──────┴──────┴──────┴──────┘  │   각 칩 ≥ 72×44pt, 가운데 정렬
└────────────────────────────────┘
```

- **초기화 버튼 제거**(키보드 한정) [추천]: 키보드는 상태가 남지 않는다. 혹시 키가 걸려 보이면(비정상 held) `blur`/`pointercancel` 처리로 해결할 문제지 버튼으로 해결할 문제가 아님. 남는 자리를 칩 4개에 준다.
- 칩은 **가운데 정렬 1줄**: 좌우 손잡이 무관하게 엄지 도달 동일. 좌우 반전 설정 불필요 [추천].
- 보조 라벨은 칩 바로 위 1줄. 전환 직후 1.5초간 진하게 → 이후 50% 불투명. 한 줄 설명(3.2)은 칩 **길게 누르기**로 툴팁 표시 [가설].
- 개발 배지("SFX B 녹음")는 `?stats=1`에서만.

### 4.2 카메라 [가설, 실기기 확인 필요]
- 현행: 타깃 위 약 57° 내려다보기(벡터 0,1.55,1). 키 윗면이 크게 보여 히트 영역에 유리.
- 스위치 차이를 보이려면 **키 옆면(이동 거리)이 보여야** 한다. 제안: **약 48~52°**로 소폭 낮추고, 앞 행 키의 옆면이 6~10pt 보이게. 키 윗면 히트 영역이 70pt 아래로 줄면 원복.
- 카메라 자동 움직임(패럴랙스·자이로) 없음. 정지 카메라가 손맛 비교에 유리하고 멀미 위험 0.

### 4.3 스위치 차이를 "보이게" 만드는 방법 (HUD 없이)

터치 입력은 압력이 없어 키가 거의 즉시 바닥까지 간다(현 down ≈ 수십 ms). **누르는 순간의 움직임 차이는 눈으로 거의 안 보인다** [가설: 실측 필요]. 그래서 차이는 ① 소리 ② 올라오는 움직임 ③ 키 흔들림 ④ 전환 순간의 연출에 싣는다.

| 프리셋 | 내려갈 때(≈20~40ms) | 바닥 | 올라올 때 | 흔들림(누른 위치 기울기) | 소리 타이밍 |
|---|---|---|---|---|---|
| 도각 | 매끈한 1단 곡선 | 둔탁, 반동 거의 없음 | 약간 느리게, 오버슈트 작게 | 중간 | 바닥에서 1회 |
| 또각 | **중간에 짧은 정체(범프)** 후 하강 | 보통 | 빠르게, 끝에서 작은 툭 | 작음 | 범프 미세음 + 바닥 |
| 찰칵 | 범프 + **작동점에서 딸깍** | 보통 | 빠르게, **올라오며 2차 딸깍** | 작음 | 작동점·바닥·복귀 3회 |
| 서각 | 매끈 | **폭신(바닥이 살짝 눌렸다 멈춤)** | 부드럽게, 오버슈트 없음 | 큼(덜그럭 대신 스르륵) | 작고 짧게 |

- 위 표는 기존 `KeyboardModel`의 스프링 파라미터를 프리셋별로 갖게 하는 수준으로 구현 가능해 보임(코드는 구현 에이전트 판단).
- **스위치 엿보기(Switch peek)** [추천]: 칩을 바꿀 때 시연 1타 대신(또는 시연과 함께) **가운데 키의 키캡이 0.5초간 살짝 들려 그 아래 스위치(투명 하우징 + 자체 팔레트 스템)를 보여주고** 다시 내려앉으며 1타. 실물에서 "키캡을 뽑아 스위치를 확인하는" 행동의 은유. 첫 전환 1회만 풀 연출, 이후는 짧게(0.2초) [가설].
  ```
   전환 직후               0.3s                    0.6s
   ┌────┐               ┌────┐  ← 키캡 들림        ┌────┐
   │ ♪  │                └────┘                    │ ♪  │ 도각!
   └────┘               ┌─▣──┐  ← 스위치 노출      └────┘ (1타)
                         └────┘
  ```
- **투명 키캡 상시 표시는 비권장**: 실사 품질·셰이더 비용 증가, "같은 키보드" 외형 변화.
- **이동량 게이지·파형 HUD는 넣지 않음**. 단 접근성 "소리 시각화" 옵션에서만(§6).

### 4.4 첫 10초 (키보드 진입) [가설]

| 시점 | 화면 | 소리 |
|---|---|---|
| 0~0.3s | 포스터(정지 이미지) | — |
| ~1~2s | 3D 판 등장, 칩 = 저장값 또는 **도각** | — |
| 무입력 1.5s | **유휴 시연**: 만→지→작 순서로 3키가 빠르게 또르륵 눌렸다 올라옴(1회) | 오디오 언락된 경우만 소리(홈 카드 탭으로 들어오면 언락됨) |
| 무입력 4s | 손가락 고스트 1회(♪ 키 위) | — |
| 첫 키 터치 | pointerdown에서 즉시 키다운 + 소리. 언락 실패 시 **키업 소리부터** 나도록(§5.2) | 첫 소리 |
| 첫 타건 후 2~3타 | 힌트 "아래에서 스위치를 바꿔보세요" 1회, 칩 줄이 살짝 반짝 | — |
| 이후 | 힌트 없음 | — |

- 링크로 `#/keyboard`에 바로 들어온 경우 첫 pointerdown이 무음일 위험. 현행 capture 언락 + keyup 소리 우선이 맞는 방향 [검증필요: iOS 실기기].
- 힌트 문구 후보: "키를 눌러보세요" → (2타 후) "스위치를 바꾸면 소리와 손맛이 달라져요".

## 7. 우선순위 — 다른 장난감과의 관계

### 7.1 입장
- 원 기획에서 키보드는 **부차 장난감**(P3 키보드 관심층 = 부차, MVP B안 "말랑이 + 키보드 축소", 프리셋 2종). 주력은 말랑이. 이 판단을 **바꿀 근거는 아직 없다** [추천].
- 근거
  1. **콘텐츠 축에서 이미 짐**: 경쟁 앱이 키캡 스위치 20종. 4종 시뮬레이터로 "스위치 앱"을 표방하면 숫자 비교에 걸린다.
  2. **소리 품질이 전부인데 아직 사람 귀 검수 0**(MVP_STATUS): 녹음 없이 4종을 늘리면 "4종이 다 비슷하다"는 최악의 결과가 날 수 있다. 4종 = 녹음 4세트(세트당 55~70샘플).
  3. **키보드 소리 자체는 흔하다**(Mechvibes 등). 차별은 "모바일 터치로 누르는 실사 3D 판 + 링크 즉시"이고, 이는 **2종으로도 증명 가능**.
  4. 반면 기술 비용은 가장 낮은 장난감(§7.6 난도 1위) → 런타임·오디오·지연 측정 파이프라인 검증용으로는 계속 가치 있음.
- 결론: **말랑이 S1·P0 게이트 통과 > 키보드 최소 개선 > (녹음 확보 시) 키보드 4종 > 음식형 스퀴시/왁뿌볼(v1.1 조건부)**. 키보드 4종은 v1.1 후보 중 "녹음만 확보되면 가장 싸게 늘릴 수 있는 것"으로 위치. [추천]

### 7.2 v1.1 전에 할 가치가 있는 최소 키보드 변경 [추천]

| # | 변경 | 비용 | 이유 |
|---|---|---|---|
| 1 | **칩 탭 = 시연 1타** | 작음 | 비교 속도 즉시 상승. 프리셋 수와 무관하게 이득 |
| 2 | **프리셋별 움직임 프로파일**(올라올 때·바닥 반동·흔들림) | 작음(스프링 파라미터) | "소리만 바뀌는 게 아니라 손맛도 바뀐다"는 핵심 가설을 녹음 없이 먼저 검증 |
| 3 | 키보드 화면 초기화 버튼 제거, `↺` 레전드 교체, 개발 배지 숨김 | 매우 작음 | 혼동 제거 |
| 4 | 기존 2종을 **메커니즘 축으로 재프레이밍**: 조약돌 → "도각(리니어·묵직)", 까랑까랑 → "또각(택타일·경쾌)" or "찰칵" | 작음, 단 현 녹음이 그 메커니즘인지 확인 필요 [검증필요] | 4종으로 갈 때의 이름 체계를 미리 시험 |

- **하지 말 것**: 4종 칩을 녹음 없이 합성음으로 먼저 출시, 2축 피커, 3D 스위치 트레이, 자석식 프리셋.
- 4종 확장의 진입 조건 [추천]: (a) 자체 녹음 4세트 확보, (b) 블라인드 청취에서 4종 구별 정확도 ≥ 80%, (c) 무음 상태 구별 테스트에서 ≥ 2종 이상 구별.

## 8. 사용성 테스트 질문

### 8.1 과제 기반 (관찰)
1. 링크로 키보드 화면에 들어온 직후, **첫 키를 누르기까지 걸린 시간**과 첫 소리가 났는가(iOS/Android, 카톡 인앱 포함).
2. 지시 없이 "다른 느낌으로 바꿔보세요" → 칩을 찾는 데 걸린 시간. 칩 대신 키를 길게 누르거나 판을 스와이프하는 사람이 있는가.
3. 4종을 모두 들어보게 한 뒤, **소리만(화면 가림)** 으로 무작위 재생 → 몇 번째 스위치인지 맞히기(구별 정확도).
4. **무음 상태**에서 4종을 바꿔 가며 눌러보게 함 → "차이가 보이나요?" 몇 종을 구별하는가.
5. 시연 1타가 있는 버전 vs 없는 버전: 4종 비교를 끝내는 데 걸린 시간·탭 수.
6. 스위치 엿보기 연출을 본 뒤 "방금 무엇이 바뀌었나요?" → "스위치"라고 답하는 비율.
7. 여러 손가락으로 화음을 칠 때 누락·잘못된 키가 있는가. 손가락이 미끄러질 때 기대한 동작(유지 vs 옆 키 입력)은 무엇인가.

### 8.2 인터뷰 (인식)
8. "도각/또각/찰칵/서각" 각각 듣기 전에 어떤 소리를 상상하는지 → 실제와 맞는가. "서각"을 이해하는가(안 되면 "툭툭").
9. 보조 라벨(리니어/택타일/클릭/저소음)이 도움이 되는가, 방해가 되는가. (일반 vs 키보드 관심층 나눠서)
10. 키보드 관심층에게: 특정 실제 스위치가 떠오르는가? 그것을 기대했는데 아니라서 실망했는가?(→ 재현 기대 관리 필요 여부)
11. 4종이면 충분한가, 부족한가. 부족하다면 "더 많은 종류"를 원하는가, "직접 조합"을 원하는가, "나란히 비교"를 원하는가?(확장 경로 우선순위)
12. 말랑이와 키보드 중 어느 쪽을 먼저 다시 열겠는가, 어떤 상황에서?(우선순위 검증)
13. 회의 중/대중교통 같은 상황에서 서각(저소음)을 고를 의향이 있는가, 아니면 그냥 무음으로 두는가.
14. 연타 2분 후 귀가 피곤한 프리셋이 있는가(찰칵 피로 가설).

### 8.3 성공 기준(초안) [가설]
- 첫 타건 ≤ 3초(언락 포함), 칩 발견 ≤ 10초(무지시 80%).
- 블라인드 소리 구별 ≥ 80%, 무음 시각 구별 ≥ 2종.
- "같은 키보드인데 스위치가 바뀐다"고 설명하는 비율 ≥ 60%.
