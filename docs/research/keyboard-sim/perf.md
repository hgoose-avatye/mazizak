## 1. 터치→소리 / 터치→화면 지연 예산

### 1.1 경로 분해

```
손가락 접촉 ─(디지타이저 샘플링·OS 처리)─> pointerdown 디스패치 ─(JS 핸들러)─> src.start(0)
   └ 오디오 스레드: 다음 렌더 퀀텀(128프레임=2.67ms@48k)에서 믹스 → 하드웨어 버퍼(baseLatency)
      → 출력 장치(outputLatency: DAC·OS 믹서, BT면 코덱 버퍼) → 귀
손가락 접촉 → pointerdown → push() → requestFrame() → 다음 vsync rAF → toy.frame + render
   → 컴포지터 → 디스플레이 스캔아웃 → 눈
```

|---|---|---|---|---|

**해석**
- 실제 기계식 키보드에서는 손가락이 키캡에 닿은 뒤 바닥에 닿기까지 수~수십 ms가 걸린다. 터치스크린에서 유리에 닿는 순간을 바닥 충돌로 보고 **바닥 충돌음(bottom-out)을 즉시** 내는 게 맞다. 클릭형의 클릭음(실물에서는 작동점에서 바닥 충돌보다 5~10ms 먼저 남)은 앞당길 수 없다. 따라서 베이크할 때 **클릭이 0ms, 바닥 충돌음이 +3~6ms** 순서가 되게 배치한다 [가설: 청취 A/B로 조정].
- 소리는 화면보다 대략 1프레임 먼저 난다. 소리가 먼저 오는 쪽이 지각상 덜 거슬린다 [추정]. 키 모양을 소리 시점에 맞춰 늦추지 않는다.
- 유휴 상태에서 GPU 클럭이 내려가 있으면 첫 프레임이 늦을 수 있다 [추정, 검증필요]. 측정 항목에 "유휴 2초 뒤 첫 탭" 케이스를 따로 둔다.

### 1.3 pointerdown / pointerup과 언락

- 터치에서 활성화 이벤트는 `pointerup`(pointerType≠mouse)과 `touchend`뿐이다. `pointerdown`은 mouse일 때만 활성화로 친다 [확인: MDN User activation].
- 그래서 **처음 한 번만** 문제가 된다. 컨텍스트가 `running`이 된 뒤에는 `pointerdown`에서 바로 재생해도 아무 문제가 없다(활성화가 필요한 건 resume뿐이다).
- 현재 홈 화면 탭에서 언락한다 [확인: MVP_STATUS, main.ts capture 리스너]. **딥링크로 `#/keyboard`에 바로 들어오면** 첫 키다운이 `pending` 상태가 된다. 그러다 손을 떼면 resume되는데, 그때까지 80ms(LATE_MS)를 넘기면 `dropped-late`로 버려진다 [확인: audio.ts]. 대응: ① 키보드 화면 진입 시 컨텍스트가 suspended면 첫 탭의 **업 사운드를 약간 강조**하고(§8.5 "놓을 때 첫 소리" 원칙), ② 안내 토스트를 1회 띄운다.
- `navigator.vibrate`도 sticky activation이 필요하다. 딥링크 첫 `pointerdown`의 `haptic(6)`은 무시될 수 있다 [추정].

### 1.4 메인 스레드 보호(소리 지연의 실제 변수)

| 위험 작업 | 현재 상태 | 권고 |
|---|---|---|
| 프리셋 전환 시 레전드 `CanvasTexture` 10장 재생성 + GPU 업로드 | 있음 [확인: visual.ts setStyle] | 레전드를 **알파 전용 텍스처 + 색은 uniform**으로 바꿔 전환 시 텍스처 작업 0 |

### 2.4 그래프와 GC

| 항목 | 현재 | 권고 |
|---|---|---|
| 보이스마다 새로 만드는 노드 | BufferSource + Gain + (StereoPanner) + (Biquad) [확인] | **BufferSource + Gain**만 만든다. 팬은 키별 고정값이므로 **키 채널 스트립(Gain → StereoPanner)을 상시** 두고, 벨로시티 로우패스가 필요하면 그것도 스트립에 둔다 |
| Gain 노드 재사용 | 없음 | 레이어 방식이면 키 이벤트 하나당 Gain 1개에 레이어 소스 여러 개를 연결한다. GainNode 풀링은 실익이 작다(disconnect·재연결 비용, 버그 위험). 노드 수 절감은 스트립으로 충분하다 [추정] |
| JS 할당 | 매 재생마다 PlayLog 객체, `voices.filter`, `recentStarts.filter` 배열 재생성 [확인] | 프로덕션에서는 로그를 끄거나 링버퍼로 바꾸고, filter는 in-place 압축으로 바꾼다. 15탭/s에서 할당량은 수 KB/s 수준이라 GC 영향은 작지만 [추정], 저가 Android의 마이너 GC 끊김을 줄이는 값싼 조치다 |
| 리미터 CPU | Compressor 1 + WaveShaper(2x 오버샘플) 1, 고정 비용 [확인] | 보이스 수와 무관하므로 유지. 보이스 32개 × (재샘플링 + 게인) 비용도 오디오 스레드 예산에 비해 작다 [추정]. **OfflineAudioContext 렌더 시간 비율**로 회귀를 감시한다(§5) |
| detune | 키별 고정값 + 무작위 → 매 보이스 재샘플링 | 비용은 작다. 그대로 둔다 |
| AudioWorklet | 미사용 [확인: §8.4] | 32보이스 이하에서는 쓰지 않는다. 단, "스위치 테스터 + 연속 레이어"에서 노드 생성 비용이 측정상 문제가 되면 그때 워크릿 믹서를 검토한다 [가설] |

### 3.1 현재 실측 [확인: m.py, public/sfx/keyboard/*.json]

| 프리셋 | down | up | spaceDown | spaceUp | 스프라이트 길이 | 디코딩 후(f32 모노 48k) | WAV 전송 |

- 로드하는 순간에는 스프라이트와 슬라이스를 함께 들고 있어 **피크가 약 2배**다. 이후 스프라이트는 GC 대상이 된다 [확인: keyboardSamples.ts].

### 3.2 목표 샘플셋 가정 [가설]

- 프리셋 하나(전체 키보드) = 일반 다운 3단 벨로시티×8테이크×180ms + 일반 업 2단×8×120ms + 스페이스 다운 8×280ms + 스페이스 업 8×200ms = **10.1초**
- 레이어 방식: 메커니즘(클릭 8×30ms, 스템 충격 3×8×60ms, 스프링 핑 6×200ms, 탑아웃 8×80ms) = 3.5초/종. 스타일(바디 다운 3×8×180ms, 바디 업 8×120ms, 스페이스 다운·업) = 9.1초/종

### 3.3 아키텍처별 메모리 (f32, 48kHz, **모노**; 스테레오면 ×2) [계산: mem.py]

| 구성 | (a) 사전 믹스 파일 | (b) 레이어 파일 + 런타임 믹스 | (b') 레이어 다운로드 + **베이크** |
|---|---|---|---|
| 활성 프리셋 1개 | 1.94MB | 2.43MB (메커니즘 1 + 스타일 1) | 베이크 결과 1.94MB (원본 레이어는 베이크 후 해제 가능) |
| 4 프리셋 전부 상주 | 7.7MB | 9.7MB (4×4 라이브러리) | 필요한 것만 |
| **5×4 = 20조합 전부 상주** | **38.7MB** | **10.4MB** | 활성 1개 + 이웃 1개 ≈ 3.9MB + 레이어 캐시 |
| 스위치 테스터(9종, 일반 키만) | 10.8MB | 7.8MB (메커니즘 9 + 스타일 1) | 10.8MB 또는 레이어 7.8MB 유지 |
| 다운로드: 4 프리셋 | WAV 3.9MB / FLAC 약 2.1MB / AAC128 약 0.65MB | 레이어 합계 기준 WAV 약 4.9MB / AAC 약 0.8MB | (b)와 같음 |
| 다운로드: 20조합 | WAV 19.4MB / AAC 3.2MB | WAV 약 5.2MB / AAC 약 0.87MB | (b)와 같음 |

**판단**
- 프리셋 4종에서는 (a)가 가장 단순하고 메모리 차이도 작다. **20조합이나 스위치 테스터부터는 (b)의 다운로드·메모리 이점이 커진다.**
- 다만 (b)를 런타임에 섞으면 §2의 보이스 비용이 생기고, 레이어 사이 위상·타이밍을 청취로 맞추는 품질 문제도 런타임에 남는다. → **(b') 베이크 권장.** 프리셋을 선택하면 메커니즘 테이크 × 스타일 테이크를 JS로 합산해 이벤트별 AudioBuffer 풀을 만든다. 예: 다운 24개 × 평균 8,600샘플 ≈ 21만 회 덧셈이라 **수 ms 이내** [추정]. 조합 수(라운드로빈 다양성)는 베이크 개수로 조절한다.
- 스타일(케이스 공명)을 컨볼루션 IR로 처리하는 안: ConvolverNode는 보이스마다 두면 비싸다. 마스터 버스에 하나만 두면 CPU는 고정 비용인데 "키 바디" 표현력이 떨어진다 [추정]. **오프라인 베이크 단계에서만** 컨볼루션을 쓰는 것은 가능하다(OfflineAudioContext).
- 품질 등급이 `saver`이면 **22.05/24kHz 샘플과 다운믹스 모노**를 쓴다. 단, 디코딩 결과는 컨텍스트 샘플레이트로 재샘플링되어 저장되므로 메모리 절감 효과가 없다 [확인: decodeAudioData는 ctx.sampleRate로 재샘플링, 코드 주석 keyboardSamples.ts]. 절감은 전송량에서만 생긴다.

| 항목 | 권고 |
|---|---|
| 지연 로드 | 키보드 진입 시 **현재 프리셋만** 로드한다(현행). 첫 소리 준비 목표: 4G에서 진입 후 1초 이내 [가설] |

| 해제 | 상주 상한 = 활성 + 이웃 1 + 최근 1 (LRU 3개). 장난감을 나가면 전부 해제한다(§8.4). 현재 캐시는 `WeakMap<ctx>`라 **컨텍스트가 살아 있는 한 해제되지 않는다** [확인: keyboardSamples.ts] → LRU를 명시적으로 추가 |

| iOS 메모리 | 디코딩된 PCM은 WebContent 프로세스 메모리로 잡힌다. 탭 한도는 비공개이고 기기 RAM에 따라 다르다 [확인: 기획서 §14 / 수치 검증필요]. 오디오 상주량 목표는 **≤ 12MB** [가설]. 텍스처와 지오메트리를 포함한 키보드 화면 전체 목표는 ≤ 150MB [가설] |

| 방법 | 절차 | 산출 |
|---|---|---|
| 240fps 촬영 | 손가락이 유리에 닿는 프레임과 화면 키가 내려가기 시작하는 프레임을 센다(1프레임 = 4.17ms). 30탭 | 터치→화면 p50/p95 |
| 2채널 녹음 | 채널 1 = 유리에 붙인 접촉 마이크(탭 충격), 채널 2 = 스피커 앞 마이크. 두 onset 차이를 자동 검출하는 스크립트 | 터치→소리 p50/p95 (스피커, 유선, BT 각각) |
| 앱 내 기록 | `latencyInfo()`(base/output), unlockLogs, eventToHandler를 "성능 정보 JSON"으로 함께 내보내기 [확인: 설정에 JSON 내보내기 있음] | 추정치와 실측의 차이를 기기별로 보정 |

## 7. 구현 순서 제안 (성능 관점)

1. **현행 수정(작음)**: 스타일 uniform화와 미리 컴파일, 알파 레전드, 스위치 인스턴싱 → 드로우콜 33 → 약 14
2. 오디오 엔진: 키 채널 스트립, 키당 상한, 우선순위 빼앗기, 로그 토글, 스프라이트 오프셋 재생
3. 로더: LRU, 이웃 프리로드, 싱크 마커, FLAC/AAC A/B
4. 레이어 다운로드 + 베이크(20조합과 스위치 테스터의 전제)
5. K1~K10 자동화를 `bench.mjs`에 추가하고, 이어서 실기기 A3 측정
